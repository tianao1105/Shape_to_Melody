# Shape to Melody（中文版）

一个把画画变成钢琴音乐的小网页应用。

你在画布上画线，应用读取线条的位置，给每段线段奏出对应的音符。在画面上越往上的位置，音越高。一条长曲线会弹很多音，一个小点只弹一个音。

差不多就这些。我做这个就是想看看一张画能不能"听上去像什么"，结果还真有点像。

线上体验：https://tianao1105.github.io/Shape_to_Melody/

> 英文版 README 见 [`README.md`](README.md)。

## 画画

五种笔触：画笔、霓虹、喷雾、书法、彩虹。五种形状：直线、矩形、圆形、心形、三角、星形。颜色一排 16 种。笔刷大小从 2 到 24。

三种画布模式：
- 普通
- 左右对称
- 万花筒（上下左右四象限镜像）

你也可以拖一张 PNG 或 JPG 进来。应用会找出图片里偏暗的部分，把它们当成你画的线。照片效果一般，简单的线稿效果还行。

## 把画变成音乐

点右边的「转换」。应用会读你画的线，给出一串音符。

三种转换模式：
- 全部转换：每一笔都变成音符
- 部分转换：在画布上拖一根范围条，只把范围里的部分变成音符
- 随机转换：从你画的线里随机挑出固定数量的音符

可以调音阶（五声、大调、小调、半音阶）、BPM（40 到 240）、采样间隔（每隔多少像素采一个音）。

点「播放」听一下。点「停止」停。屏幕右边那个小亮点会显示当前正在弹的琴键。

## 用手编辑音符

转换出音符之后，点画布右边的「琴谱」。音符会变成有颜色的小方块，铺在一个钢琴卷帘上。把一个方块往上下拖，可以改音高；往左右拖，改时间；按 Delete 删一个。

如果你手动改完之后又点了一次「转换」，应用会先弹一个确认框，免得你的修改被覆盖丢了。

## 图层

点画布上方的 `+` 加一个图层。每个图层有自己的画、自己的颜色、自己的乐器、自己的音量。8 种乐器可选：钢琴、电钢琴、风琴、弦乐、拨弦、钟声、马林巴、木琴。

可以把伴奏放一个图层，旋律放另一个。播放的时候自动混在一起。

## 保存和分享

- 保存：导出一个 `.s2m.json` 项目文件，里面是完整的作品数据。
- 打开：把 `.s2m.json` 文件读回来。
- 分享：生成一段链接，把你整张画压进 URL 里。把这个链接发给朋友，对方打开就能看到你画的东西，不需要服务器。画得少链接就短，画太多链接会超长，应用会提示你用"保存"导文件分享。

应用还会自动存到你浏览器里。下次打开页面，顶部会弹一个小提示问你要不要继续上次的作品。

## 主题

16 套配色。8 套浅色，8 套深色。点 header 上的太阳/月亮图标切换浅色/深色，再点彩色圆点选具体一套。钢琴键、音符方块、上传区都会跟着主题色变。

## 语言

中文和英文。右上角的按钮（`EN` 或 `中文`）切换。

## 本地运行

就是一堆静态文件。clone 仓库，开个本地服务器，浏览器打开就行。

```bash
git clone https://github.com/tianao1105/Shape_to_Melody.git
cd Shape_to_Melody
python3 -m http.server 8000
```

然后浏览器访问 `http://localhost:8000`。

也可以直接双击 `index.html` 打开，但有些浏览器禁止本地文件播音频，所以开个小服务器更稳。

不需要 `npm install`，不需要打包构建。

## 用到的技术

- 原生 JavaScript + Canvas API 做画图
- [Tone.js](https://tonejs.github.io/) 做声音
- [lamejs](https://github.com/zhuker/lamejs) 做 MP3 导出
- 浏览器自带的 `CompressionStream` 给分享链接做 gzip
- CSS 容器查询（`cqw` 单位）让布局跟着画布尺寸缩放，不是跟着视口缩

没有框架，没有打包器，没有后端。

## 导出格式

- MIDI：拖进 DAW 用
- WAV：无损音频
- MP3：体积小，方便分享

三种都在浏览器里渲染，数据不离开你的电脑。

## 教程

第一次打开页面会自动播一个短教程，自己画一条波浪线、转换、播放给你看。想再看一遍，点 header 上的 `?` 按钮。

## 键盘快捷键

- `Ctrl/Cmd + Z`：撤销
- `Ctrl/Cmd + Shift + Z` 或 `Ctrl + Y`：重做
- 在琴谱视图里按 `Delete` 或 `Backspace`：删除选中的音符

## 开发过程中的选择

几个早期定下来的、影响整个项目方向的决定。

**用原生 JS，不上框架。** 想完全省掉打包步骤。没有 `node_modules`，没有 webpack，不用等。打开就能用。代价是要多写一些样板代码，但项目本来就不大，能接受。

**Y 轴对应音高，X 轴对应时间。** 越往上画，音越高。这是最直觉的方式。另一种方案是 X 轴对应音高、每一笔走一段时间，但人画的形状不一定从左到右，那种映射很容易崩。

**按弧长采样。** 沿着线每隔 N 像素采一个音，不是每 N 个原始点采一个。这样一条曲线和同样形状的直线发出的音一致。如果按原始点，画得快和画得慢会出不一样的音，我不想要这个效果。

**全客户端。** 没有后端。保存是文件，分享是 URL。不需要账号、不用注册、没有数据库。这让部署变得很简单（GitHub Pages 就够），用户数据也不出他自己的机器。

**单条笔画的颜色不进分享链接。** 如果带上，链接会几乎翻倍长，但用户感受不大。接收方看到的是图层默认色的笔画。够用了，反正核心是"看我画了什么"。

**用 CSS 容器查询，不用视口单位。** 这点花了我一段时间才搞明白。一开始图层标签用 `vw` 算尺寸，结果只有窗口变小才会缩；可是在宽屏上侧栏占很多空间的时候，画布其实是小的，但标签还是大的。容器查询（`cqw`）读的是画布本身的宽度，正合需要。

**自动保存存 PNG + 笔画数据，分享链接只存笔画。** 自动保存可以放到 local storage，几 MB 都不算多。分享要装进 URL，只能带笔画矢量。接收方那边再跑一次「转换」就能还原音符，听上去和发送方一样。

## 走过的弯路

试过但没成的方案。

**先弹预览框再转换图片。** 一开始上传图片之后，我加了一个弹窗显示这张图，问你要不要点"转换"才动手。本意是让用户有控制感。实际上多了一个莫名其妙的步骤。大家就想看到图片直接变成线、自己去玩。第一轮反馈之后我就删了。

**用距离链稀疏化音符。** 第一次想让"采样间隔"滑杆对图片导入的音符起作用。原来的滑杆只控制每条笔画内部的采样密度，所以一张密集的图（几百条小笔画）调滑杆几乎没反应。我试了一个方法：按生成顺序遍历音符，丢弃那些距离上一个保留点太近的。结果还是没什么变化，因为图片来的笔画散布在整张画布上。换成"网格分桶"才有效（把每个音符投到一个格子里，每个格子只留一个）。

**用 vw 做响应式。** 图层标签的 `clamp()` 一开始用视口宽度。在手机上看着没问题，但在桌面上、画布被侧栏挤窄了，标签还是原尺寸。问题是侧栏宽度啃掉视口宽度，但是 vw 看不到。最后是容器查询解决了。

**画布提示一直亮。** 早期，多图层情况下，清除了其中一个图层，"在这里画点什么"的提示就会闪回来，即使其他图层还有画。清除按钮是无条件把 `has-drawn` 这个 class 移掉的。花了我一阵子才意识到这里应该看所有图层，而不是只看活动图层。

**在沙盒里 commit 代码。** 我有一次在工具的沙盒里跑了 `git status`。沙盒删不掉自己产生的 `.git/index.lock`。结果 GitHub Desktop 一直拒绝 commit。最后我手动去文件夹里把锁文件删了。

**把项目放在 OneDrive 的"文档"目录下。** 文件一直被中途截断。花了好几天才意识到是 OneDrive 同步在我写文件时干涉。把项目从 `OneDrive/文档/GitHub` 搬到 `Documents/GitHub` 都没用，因为 Windows 默认把"文档"重定向给 OneDrive。真正的解法是关掉 OneDrive 对"文档"文件夹的备份。

## 关键突破

**教程那个 bug 跟中文无关。** 我一开始以为只有中文模式下教程第一步的高亮框会跑偏。结果是只要用户在琴谱视图下点了帮助按钮重看教程，就会出问题。主画布 `display: none`，bounding box 是 0，高亮框就钉到屏幕左上角去了。修复就一行：教程一开始强制切回画布视图。

**用网格分桶稀疏化图片音符。** 距离链方法失败之后，我试了一种新做法：按"采样间隔"大小把整张画布切成方格，每格只留一个音符。终于让"采样间隔"滑杆对图片有效了。同样的间隔设置下，从大约 1100 个音符降到 50 个。

**容器查询。** 一旦认清问题（视口单位不反映画布尺寸），修法就很直接。在画布列上加 `container-type: inline-size`，把 `vw` 换成 `cqw`，搞定。图层标签现在跟画布同步缩。

**毛玻璃按主题染色。** 上传区原本是写死的白色磨砂 + 2px 模糊。在深色主题上看着很违和（白色配深绿没道理）。换成 `color-mix(in srgb, var(--surface) X%, transparent)` 配上更强的模糊，每个主题都能取到自己的表面色，所有主题看起来都像是有意为之了。

**`themechange` 事件。** 切换主题对新画的内容生效，但已经画好的钢琴键和音符块颜色不变 —— 因为它们是画到 canvas 像素里的，改 CSS 变量并不会重画像素。让 `applyTheme()` 派发一个自定义 `themechange` 事件，让 canvas 视图监听重画，问题就解决了。

## 我怎么和 AI 合作（prompting）

这个项目我是和 Claude（Anthropic 的对话 agent）一起做的。不是"ChatGPT 帮我做好了"的做法，更像一来一回地配合，我开车它打字。

我固定下来的工作模式：

1. 一次只问一个小事。"给每个图层标签加一个删除按钮"，而不是"做一套图层系统"。
2. 运行一下看结果。如果不对，用大白话说哪不对（"这个 band 太小了"、"桌面上还是不缩"），让它再试。
3. 如果它给出一个看上去高级的方案，我会要求一个更简单的版本。简单版几乎总是正确的。
4. 我永远先看 diff 再接受。有两次我抓到了它加进去了和文件其他部分不搭的逻辑。
5. 任务列表写在外面（写在对话之外的地方），方便第二天回来继续。

AI 擅长的事：

- 样板代码。快速写新的 CSS 规则、新的 HTML 结构、跟旁边函数风格一致的新函数。
- 一旦我说清现象，它能定位 bug。"换主题之后画布没重绘"一轮就给出了正确答案。
- 重构（结构错的时候帮我把代码挪到正确的位置）。

AI 不擅长的事：

- 不知道该停下来问。它常常直接铺一个方案下去，而不是先问我倾向哪个选项。
- 看不到文件系统层面的问题。OneDrive 截断那个事它完全看不到，只会一遍一遍重试写文件，但磁盘那边数据已经被悄悄截断了。
- 视觉判断。"这样好看吗？"这种问题它没法答，得我亲眼看。

如果重新做一遍，AI 用法基本一样，但 UX 品味的事我就不问它了。

效果好的 prompt 例子：

- "我手动改过琴谱里的音符之后，再点 Convert 应该先弹一个确认框。取消就什么也不做，确认就照常 Convert。"
- "画布两端的书签标签好像没对齐。它们是按整个 canvas-area 居中的，不是按画布本身。改成跟着画布走。"
- "图片导入的画布，调采样间隔不会改变音符数量。查一下原因再修。"

效果差的 prompt 例子：

- "做得好看点。" —— 太宽泛。改成："把书签标签的阴影缩到几乎看不到。"
- "重构 canvas 代码。" —— 没有目标。改成："把 `_strokeSegment` 里画刷样式的部分抽到独立的 helper 里，这样我可以在 share-restore 里复用。"

## 参考资料

做这个项目的时候我查过这些东西。

- [Tone.js 文档](https://tonejs.github.io/) —— 声音引擎。Sampler 和 Transport 这两个类挑了大部分活。
- [lamejs](https://github.com/zhuker/lamejs) —— 浏览器内 MP3 编码。
- [MDN: Canvas API](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API) —— 画图原语。`getImageData` 和 `putImageData` 是撤销/重做的核心。
- [MDN: CSS Container Queries](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_container_queries) —— 解决了布局尺寸跟画布缩放的问题。
- [MDN: CompressionStream](https://developer.mozilla.org/en-US/docs/Web/API/CompressionStream) —— 分享链接的 gzip。
- [MDN: color-mix()](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/color-mix) —— 主题感知的毛玻璃。

"画画转音乐"这个想法不是新的。2015 年前后陆续有一些类似的应用。我想看看在一个纯前端单页里能把打磨度和导出流程做到多深。

## 反思

几件做完之后才想明白的事。

最难的不是声音，也不是画布，是把那些小细节弄对。书签标签的阴影大小。提示文字什么时候消失。音符方块该是什么颜色。每一项都要单独反复"这样还不对"。整个项目大概 60% 时间都花在打磨上。

移动端测试应该更早做。我先把桌面布局做完，结果发现 header 大概 500px 宽，Android Chrome 根本不会自动换行。iOS Safari 处理得没问题，所以我以为没事。等我意识到，已经只能往一个本来不是为换行设计的布局里硬塞 `flex-wrap: wrap` 了。下个项目，移动端 day-1 就上。

我也希望一开始就用二进制做分享格式。JSON 版本对小作品够用，但稍微超过 50 笔的图就顶到 URL 上限了。二进制能多塞不少。权衡是复杂度，我当时想尽快上线。

采样间隔滑杆有个隐性的 UX 陷阱。对手绘形状是好用的（"间隔 = 两个音之间的弧长"），但图片导入的笔画又短又密，同一个滑杆的语义就不一样了。我用网格分桶补了这个洞。如果一开始就想到，可能会让图片导入直接生成更少、更长的笔画。

下次会更早做保存和恢复。我大概第 3 周才加上 autosave。在那之前丢了好几次测试的草稿。如果 day-1 就有 autosave，我能多收到一些"用户实际用得多的是哪些功能、多久用一次"的数据。

跟 AI 协作改变了我对"项目范围"的思考。当样板代码变便宜了，会很想不停加新功能。我得主动按住自己问"我是真想要这个，还是只是因为加进去很容易？"。便宜的劳力是把双刃剑。

我比较满意的部分：主题做得比我预想的好。钢琴键真的跟着主题色变，给应用了一种单一配色给不了的一致感。开场动画很傻气，但我居然没看腻。
